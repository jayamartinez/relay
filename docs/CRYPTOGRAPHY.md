# Cryptography — Relay protocol v1

This documents implemented constructions, not an independent audit. The cryptographic protocol needs specialist review before a public release.

## Encoding and randomness

All secret generation uses `crypto.getRandomValues`. IDs use `crypto.randomUUID`. The account number is 24 unbiased decimal digits (~79.7 bits): bytes >=250 are rejected before reduction modulo ten. Leading zeros are preserved. Strip whitespace, require exactly 24 digits, then compute SHA-256 over UTF-8 digits; the lowercase hex digest is the server handle. The number is **not** encryption or authorization material.

Cryptographic JSON is UTF-8 with recursively sorted object keys (lexicographic comparison), original array order, omitted undefined object fields and finite numbers. Binary fields use standard base64. The recovery display uses 64 hexadecimal digits grouped in fours, retaining all 256 secret bits.

## Keys

| Material | Construction / storage | Purpose |
| --- | --- | --- |
| Workspace root (WRK) | 32 random bytes; encrypted in the local vault | Epoch-specific workspace confidentiality |
| Device signing pair | P-256 ECDSA / SHA-256; non-extractable private CryptoKey in IndexedDB | Requests, operations, snapshots and membership changes |
| Device agreement pair | Separate P-256 ECDH; non-extractable private CryptoKey in IndexedDB | Root-key provisioning |
| Local vault key | Non-extractable AES-256-GCM CryptoKey in IndexedDB | Encrypt account state, root, journal and mapping |
| Recovery secret R | 32 random bytes, shown during setup only | Encrypt recovery private-key package |
| Recovery signing pair | Separate P-256 ECDSA | Recovery enrollment authorization |
| Recovery agreement pair | Separate P-256 ECDH | Recover current root, including after rotation |
| Pairing ephemerals | New P-256 ECDH pair and random 32-byte commitment nonce per participant/request | SAS authenticated exchange |

Public EC keys are SEC1 uncompressed raw public-key exports. Recovery private-key exports use PKCS#8 inside an encrypted package. Recovery private keys are extractable only while creating that package; recovered keys are imported non-extractable. Device and pairing private keys are never exported. Cryptographic key objects use IndexedDB structured cloning, not plain JSON in `chrome.storage.local`.

## AEAD and derivation

AES-256-GCM uses a fresh random 96-bit nonce on every encryption and a 128-bit tag. Random nonces have negligible but nonzero collision probability; this is not a mathematical uniqueness claim across arbitrarily many encryptions. There is no reused fixed encryption nonce. Nonces are generated by Web Crypto, not server or caller input. Epoch changes generate a new independent root.

HKDF uses SHA-256, 256-bit output, UTF-8 salts/info as below. Derived AES keys are non-extractable.

| Key | Input secret | Salt | Info |
| --- | --- | --- | --- |
| Operation | WRK | account handle | `relay/operation/v1/{epoch}` |
| Snapshot | WRK | account handle | `relay/snapshot/v1/{epoch}` |
| Recovery wrap | R | account handle | `relay/recovery-wrap/v1` |
| Device root box | ephemeral/static ECDH shared secret | account handle | `relay/device-wrap/v1/{epoch}/{recipient}` |
| Pair wrap | ephemeral/ephemeral ECDH secret | base64 SHA-256 canonical transcript | `relay/pair-wrap/v1` |
| SAS bits | same ECDH secret | same transcript hash | `relay/pair-sas/v1` |

The SAS is the first unsigned big-endian 32 bits of the HKDF SAS output modulo 1,000,000, padded to six digits. There is a tiny modulo bias. Matching SAS is a probabilistic (~one-in-a-million per properly committed attempt), user-assisted authentication check—not a signature replacement or a 256-bit authentication code. The pair-wrap key is derived and independently tested; actual root delivery uses the recipient's long-term agreement key after SAS approval and is bound by the signed membership transition.

## Authenticated fields

- Workspace AEAD AAD is the complete header: version, account, epoch, sender, sender sequence, base revision, and payload type. An ECDSA signature covers `{header,cipher}` including nonce/ciphertext. Server-assigned revision is outside the envelope; contiguous revision and sender sequence checks protect against casual omission/replay, not all malicious-server equivocation.
- Root-box AAD: version, account, epoch, recipient, `type: root-box`, and ephemeral public key. Each box uses a fresh ephemeral ECDH pair. The box plaintext is `{root: base64(WRK)}`.
- Recovery-package AAD: version, account, `type: recovery-identity`. The plaintext contains the recovery signing/agreement private keys and corresponding public keys, which the receiver compares to the published recovery record.
- Local-state AAD: `{type: relay-local-state, version: 1}`. Its random vault key is profile-local.
- Authentication signatures cover version, account, device ID, purpose, random server nonce, expiration and SHA-256 of the exact request payload. Challenges are persisted, expire in 30 seconds and are consumed once before signature verification.

## Recovery improvement over a stored verifier

The server does not store a shared recovery-auth bearer secret or a value from which an encryption key can be derived. Instead it stores a recovery **public signing key**, public agreement key and the encrypted private-key package. R never leaves the client. Possession of R decrypts the private package locally and enables a signed recovery challenge response.

At creation and every rotation, the WRK is also wrapped to the recovery public agreement key. A recovered client verifies the complete membership chain, unwraps the current recovery root box, and signs a one-device membership addition with the recovery signing key. This supports recovery after revocation without requiring authorized devices to retain R. Losing R and all authorized devices loses access. Recovery-secret replacement/reissue is not implemented.

## Pairing and membership

Both sides commit to SHA-256(canonical `{ephemeral,random}`) before either learns the other's reveal. Each pins the first counterpart commitment. The transcript contains protocol/account, unique request ID, exact expiry, both identities/public keys, both commitments and both reveals. Replacing identity or agreement keys changes the SAS; changing a reveal without its precommitted hash is rejected. Users must compare codes on both screens. Never approve an unexpected request.

Genesis is self-signed by its sole creator. Every later control record signs the previous record's hash, monotonically increasing generation, epoch, actor, member public keys, stable recovery record and per-recipient root boxes. An existing member or the recovery signing identity may authorize additions. Removing exactly one member requires a new epoch and reprovisioning; retained public keys cannot silently change. Enrollment cannot replace existing root boxes. The receiver trusts the approved counterpart via SAS and pins that signed membership head. Recovery anchors verification using the secret-decrypted recovery identity and the complete signature chain.

All current members are account administrators in v1. Membership is not a multi-owner consensus system. A malicious authorized device already knows the WRK and can share it or authorize others. Signatures distinguish trusted devices from the untrusted relay, not a hostile authorized administrator.

## Revocation and limitations

Revocation generates an independent WRK and encrypts a current snapshot under the new epoch. Only retained member public agreement keys and the recovery public agreement key receive boxes. The server atomically commits membership/snapshot/log pruning and rejects the removed device's future challenges. Other clients verify the signed chain before accepting new keys. An online removed client verifies the removal chain, clears its vault/Relay storage and disconnects; it does not close browser tabs.

Old root boxes in signed history remain ciphertext under their original recipient keys. Revocation cannot erase historic data or keys already observed. It is not forward secrecy against later endpoint compromise. A recovery-secret holder remains an authorization authority until a future explicitly implemented recovery replacement mechanism exists.

Non-extractable keys prevent routine export, not use by malicious code executing as the extension. A compromised profile/OS/browser/build can decrypt state or invoke keys. JavaScript garbage collection does not guarantee secret memory erasure. See [threat model](THREAT-MODEL.md).
